Workshop Results Evaluation

This section consolidates evidence and evaluates the AWS network monitoring implementation.

The evaluation uses actual data from:

  • Connectivity tests.
  • VPC Flow Logs.
  • CloudWatch metrics and alarms.
  • Amazon SNS alert emails.
  • The monitoring dashboard.
  • Troubleshooting results.

Screenshots from previous sections can be reused when they contain the information required for evaluation.

1. Prepare the Evaluation

Use US East (N. Virginia) — us-east-1 when opening metrics, logs and alarms.

Review the following resources:

Resource Value
Log group /workshop/network/flowlogs
Metric namespace Workshop/Network
Metric name Rejected8080Flows
Alarm aws-network-workshop-rejected-8080
SNS topic aws-network-workshop-alerts
Dashboard aws-network-workshop-dashboard

Select one test run from section 5.5 for comparison.

Check source and destination addresses, ports and timestamps to ensure that the evidence belongs to the same test run.

2. Review the Monitoring Dashboard

Open:

CloudWatch → Dashboards → aws-network-workshop-dashboard

Select a time range containing the test and choose Refresh.

Verify the three components:

Component What to Verify
Metric graph Rejected8080Flows contains test data, using Sum and a five-minute period
Alarm status The correct alarm name and its current state
Log analysis table Appropriate results in action, dstPort and FlowRecords

The alarm status widget displays the current state. The alarm may have returned to OK after the test.

Use the alarm History to verify the earlier alert rather than relying solely on the dashboard’s current status.

4. Compare Timestamps and Evaluate Latency

4.1. Collect the Timestamps

Open:

CloudWatch → Alarms → aws-network-workshop-rejected-8080 → History

Find the ALARM transition for the selected test and record its time.

Compare these timestamps:

Timestamp Meaning Source Actual Value
T0 Test start time Get-Date or the time recorded in section 5.5 —
T_flow Flow record time Timestamp in CloudWatch Logs —
T_alarm ALARM transition time Alarm History —
T_email Email receipt time Subscribed mailbox —

Use the same time zone when comparing timestamps.

Vietnam time = UTC + 7 hours

The CloudWatch timestamp of a flow log record corresponds to the flow’s start time. The time CloudWatch receives the record is a separate timestamp.

Use the actual recorded T0 when measuring latency from the beginning of the test.

Capability Evaluation

Monitoring data generation The metric filter converts matching records into data points

Mark a capability as verified only when supporting evidence is available.

Infrastructure in this workshop is provisioned through the AWS Console. The configured automation covers log collection, metric generation, alarm evaluation and notification delivery.

6. Record the Limitations

6.1. Filter Scope

The metric filter monitors specific source and destination addresses and destination port 8080.

Update the filter when an address changes.

6.2. Delivery Latency

Flow Logs require aggregation and delivery time. A one-minute aggregation interval does not guarantee that the complete alerting process finishes within one minute.

6.3. Interpretation of Counts

Rejected8080Flows counts matching log records.

The record count can differ from connection attempts, page refreshes or packet counts because traffic is aggregated into flow records.

6.4. New and Missing Data

Metric filters process new data after creation and do not backfill existing logs.

Missing data treatment can affect an alarm’s OK state. Compare logs, metrics, alarm history and emails to evaluate the complete process.

6.5. Notification Conditions

Alarm notifications are triggered by relevant state transitions. Additional test connections do not create a new email while the alarm remains in ALARM.

8. Completion Criteria

  • Evidence from the same test run is compared.
  • The evaluation table reflects actual results.
  • Available timestamps are recorded with supporting evidence.
  • Measurements lacking sufficient data are marked Not measured.
  • System capabilities and limitations are assessed.
  • Required evidence screenshots are saved.
