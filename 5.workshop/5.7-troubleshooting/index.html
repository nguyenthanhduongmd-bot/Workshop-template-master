Troubleshooting the Monitoring System

This section explains how to diagnose issues involving VPC Flow Logs, CloudWatch metrics, alarms and Amazon SNS.

Each scenario follows this structure:

  1. Symptom.
  2. Cause.
  3. Investigation and resolution.
  4. Verification evidence.

Previously captured error screenshots can be compared with the configuration and results after correction.

1. Preparation

Use US East (N. Virginia) — us-east-1 when checking the workshop resources.

Resource Name
Flow Logs IAM role workshop-flowlogs-role
Log group /workshop/network/flowlogs
Metric filter rejected-tcp-8080
Metric namespace Workshop/Network
Metric name Rejected8080Flows
Alarm aws-network-workshop-rejected-8080
SNS topic aws-network-workshop-alerts

Before repeating a test, verify the client’s public IP and the EC2 addresses.

Check the client’s public IP at:

https://checkip.amazonaws.com/

If it has changed, update the HTTP security group rule’s Source and the metric filter’s srcaddr.

2. Workshop/Network Metric Is Missing

2.1. Symptom

The metric selector does not display the Workshop/Network namespace or Rejected8080Flows metric.

2.2. Possible Causes

  • The metric filter has not been created.
  • Configuration was entered but not saved.
  • The namespace or metric name is incorrect.
  • No data points have been published.
  • The filter does not match the test traffic.

2.3. Investigation and Resolution

Open:

CloudWatch → Logs → Log Management → /workshop/network/flowlogs → Metric filters

If the page shows Metric filters (0), create the metric filter.

If the filter exists, select rejected-tcp-8080 → Edit and verify:

Setting Value
Filter name rejected-tcp-8080
Metric namespace Workshop/Network
Metric name Rejected8080Flows
Metric value 1
Default value 0
Dimensions Leave empty

Compare the filter pattern with:

[version, accountid, interfaceid, srcaddr = "1.55.6.233", dstaddr = "10.10.1.130", srcport, dstport = 8080, protocol = 6, packets, bytes, start, end, action = "REJECT", logstatus = "OK"]

In this example:

  • 1.55.6.233 is the test client’s public IP.
  • 10.10.1.130 is the EC2 private IPv4 address.

Replace these addresses if they have changed. Do not append /32 to srcaddr.

Complete the save steps, then generate new test traffic to port 8080.

Metric filters process new data after creation and do not backfill existing logs.

3. The Graph Uses Average Instead of Sum

3.1. Symptom

The graph displays fractional values while the intended view is the total count of matching records.

3.2. Cause

The graph’s statistic is set to Average.

Average represents the mean value. Sum represents the total value within the selected period.

3.3. Investigation and Resolution

Open:

CloudWatch → Metrics → Classic metrics

Select:

Workshop/Network → Metrics with no dimensions → Rejected8080Flows

Under Graphed metrics, configure:

Setting Value
Statistic Sum
Period 5 minutes
Time range A range containing the test

Choose Refresh and hover over a data point to inspect its value.

Changing the graph statistic changes only the displayed view. Check the alarm separately to verify that it also uses Sum and a five-minute period.

Screenshot 02: Capture the metric name, Sum statistic, five-minute period and test data.

4. Test-NetConnection Is Not Recognized

4.1. Symptom

The command returns:

'Test-NetConnection' is not recognized as an internal or external command

4.2. Cause

The command is being run in Command Prompt, while Test-NetConnection is a PowerShell cmdlet.

4.3. Investigation and Resolution

In Command Prompt, enter:

powershell

When the prompt begins with PS, run:

Get-Date
Test-NetConnection -ComputerName 98.92.170.157 -Port 8080

Replace the address if the EC2 public IPv4 address has changed.

With port 8080 blocked in this workshop, the expected result is:

TcpTestSucceeded : False

This shows that the command executed and the TCP connection did not succeed. Compare it with a matching REJECT record in Flow Logs to verify that the traffic reached AWS.

Screenshot 03: Capture PowerShell showing the command, RemotePort 8080 and test result.

5. The Alarm Is in ALARM but No Email Arrives

5.1. Check the Email Subscription

Open:

Amazon SNS → Topics → aws-network-workshop-alerts → Subscriptions

Verify that the email subscription is confirmed.

If it shows Pending confirmation:

  1. Open the subscribed mailbox.
  2. Find the AWS confirmation email.
  3. Choose Confirm subscription.
  4. Return to SNS and refresh the page.

5.2. Test SNS Email Delivery

In aws-network-workshop-alerts, choose Publish message.

For Subject, enter:

Workshop 5.7 - SNS delivery test

Under Message body, select Identical payload for all delivery protocols and enter:

This message tests email delivery from the AWS network workshop SNS topic.

Choose Publish message, then check the mailbox and Spam/Junk folder.

Receiving the message provides evidence that SNS can deliver to the mailbox at the time of the test.

This test verifies SNS email delivery. Continue checking the alarm action to validate notifications originating from CloudWatch.

Screenshot 04: Capture the received test email, including its subject and message.

5.3. Check Alarm Actions and History

Open:

CloudWatch → Alarms → aws-network-workshop-rejected-8080

Verify:

Location What to Check
Details Actions enabled
Actions In-alarm notification targets the correct SNS topic
History State transition times and action execution results
SNS access policy CloudWatch publishing is permitted for the appropriate alarm ARN

The SNS topic must be:

aws-network-workshop-alerts

In the SNS access policy, verify:

  • Service principal: cloudwatch.amazonaws.com.
  • Allowed action: sns:Publish.
  • Resource: the correct SNS topic ARN.
  • SourceAccount and SourceArn conditions match the workshop account and alarm.

CloudWatch invokes notification actions when the alarm changes state. Additional connection attempts do not generate a new email while the alarm remains in ALARM.

To test a new transition, stop generating traffic and wait for the alarm to return to OK. Then repeat the test from section 5.5.

Screenshot 05: Capture History showing the state transition and action execution result.

6. Flow Logs Are Missing or Report Access Errors

Open:

VPC → Your VPCs → select the workshop VPC → Flow logs

Inspect the status and error information.

Symptom Investigation
Active but no records Generate new traffic, verify the destination log group and allow time for delivery
No records in the selected period Expand the time range or use Custom to include the test
Access error Check the IAM role, CloudWatch Logs permissions and trust relationship
SKIPDATA records Investigate skipped records and available delivery error information

Initial records can take ten minutes or longer to appear.

For an Access error, open:

IAM → Roles → workshop-flowlogs-role

Verify:

  • The role can publish to the workshop log group.
  • Policy ARNs use the correct Region and account.
  • The trust relationship allows vpc-flow-logs.amazonaws.com to assume the role.

An Active status describes the flow log’s status. Verify actual records to confirm delivery.

Similarly, missing data treatment can affect an alarm’s OK state. Use the underlying data and notification evidence to validate the complete system.

7. Record the Resolution

For each issue actually encountered, record:

Item Information
Symptom Observed error or behavior
Cause Cause established through investigation
Resolution Actions performed
Verification Results after correction
Evidence Relevant before-and-after screenshots

Scenarios that were not encountered can be documented as diagnostic guidance rather than reported as actual incidents.

8. Completion Criteria

  • The metric filter and its IP conditions are verified.
  • The graph statistic and period are checked.
  • The connectivity test runs in PowerShell.
  • The SNS subscription and email delivery are checked.
  • Alarm Actions and History are inspected.
  • Findings and appropriate evidence screenshots are recorded.
