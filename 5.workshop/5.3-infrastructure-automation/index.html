Network and EC2 Deployment

1. Objectives

This section explains how to create the network infrastructure and configure an EC2 instance to install Nginx automatically through user data.

The tasks include:

  1. Create a VPC, a public subnet, and a private subnet.
  2. Verify route tables and the internet gateway.
  3. Create a security group that allows HTTP access from the workshop client’s IP address.
  4. Configure EC2 and enable EBS volume encryption.
  5. Enter user data to install Nginx automatically.
  6. Launch EC2 and record the information required for monitoring.

The deployment shown in the screenshots uses United States (N. Virginia) — us-east-1. The EC2 configuration screenshot shows a Canonical Ubuntu 26.04 AMI.

Region consistency: If you continue with the deployment shown in these screenshots, update the Region in sections 5.1, 5.2, and the monitoring configuration in section 5.4 to us-east-1. The aws:RequestedRegion conditions and ARNs containing a Region in the permissions policies must also be updated accordingly. Editing Markdown does not change AWS resources or permissions.

3. Create the VPC and Subnets

If the workshop VPC already exists with the correct configuration, inspect it and continue to section 4.

  1. Open the VPC service.
  2. Confirm that the selected Region is United States (N. Virginia).
  3. Choose Create VPC.
  4. Under Resources to create, select VPC and more.
  5. Enable Name tag auto-generation and enter the prefix aws-network-workshop.
  6. Apply the following configuration:
Field Value
IPv4 CIDR block 10.10.0.0/16
IPv6 CIDR block None
Tenancy Default
Number of Availability Zones 1
Number of public subnets 1
Number of private subnets 1
NAT gateways None
VPC endpoints None
Enable DNS resolution Enabled
Enable DNS hostnames Enabled
  1. In the subnet configuration area, expand Customize subnets CIDR blocks.
  2. Enter:
Subnet IPv4 CIDR
Public subnet 10.10.1.0/24
Private subnet 10.10.2.0/24
  1. Review the Preview panel.
  2. Choose Create VPC and wait for completion.

The public subnet hosts the EC2 instance running Nginx. The private subnet demonstrates network separation and contains no EC2 instance in this lab.

4. Inspect the Public Subnet

  2. Select the workshop’s public subnet.

5. Verify Route Tables

5.1. Public Route Table

  1. On the subnet details page shown in screenshot 1, locate Route table.
  2. Select the blue link for aws-network-workshop-rtb-public.
  3. Open the Routes tab.
  4. Verify the following required routes:
Destination Target
10.10.0.0/16 local
0.0.0.0/0 An internet gateway with an ID beginning with igw-

igw-... is a placeholder. In the AWS console, select the actual internet gateway attached to the workshop VPC.

If the default route is missing:

  1. Choose Edit routes.
  2. Choose Add route.
  3. Enter 0.0.0.0/0 for Destination.
  4. Under Target, select Internet Gateway.
  5. Select the workshop VPC’s internet gateway.
  6. Choose Save changes.

5.2. Private Route Table

  1. Open VPC → Subnets.
  2. Select the private subnet with CIDR 10.10.2.0/24.
  3. Open the Route table tab.
  4. Verify the local route:
Destination Target
10.10.0.0/16 local

The lab design requires the private subnet to have no default route to an internet gateway or NAT gateway.

6. Create the Security Group

6.1. Enter the Security Group Details

  1. Open EC2 → Security Groups.
  2. Choose Create security group.
  3. Enter:
Field Value
Security group name aws-network-workshop-web-sg
Description HTTP access from workshop client
VPC The workshop VPC

6.2. Configure the Inbound Rule

Under Inbound rules, choose Add rule and set Type → HTTP.

In the screenshot:

  • Type is set to HTTP.
  • Protocol is TCP.
  • Port range is 80.
  • Source type is still Custom.
  • The Source field is empty.

Complete the source configuration:

  1. Click an empty area to close the suggestions currently open in the Source field.
  2. Open the Source type dropdown, which currently displays Custom.
  3. Select My IP.
  4. Confirm that AWS fills in the workshop client’s public IP address in the format x.x.x.x/32.

Save the following inbound rule:

Type Protocol Port range Source
HTTP TCP 80 The workshop client’s public IP address /32

Leave port 8080 absent from the inbound allow rules for the later REJECT test. This lab does not require an SSH rule on port 22.

6.3. Verify Outbound Access and Save

  1. Confirm that outbound IPv4 traffic allows All traffic → 0.0.0.0/0 so EC2 can download installation packages.
  2. Choose Create security group.
  3. Open the security group you created.
  4. Under Inbound rules, confirm that the HTTP 80 rule uses the workshop client’s IP address with /32.
  5. Record the source IP address for comparison with flow logs later.

7.4. Enable Root Volume Encryption

Complete these steps before launch:

  1. In Configure storage, select the blue Advanced link at the upper right.
  2. Expand the root volume configuration if it is collapsed.
  3. Locate Encrypted or Encryption.
  4. Change Not encrypted to Encrypted / Yes.
  5. If prompted to select a KMS key, use the default EBS key aws/ebs.
  6. Verify that Delete on termination is enabled.
  7. Confirm that the final configuration displays Encrypted.

Screenshot 3 records the volume before encryption was enabled. Capture an additional screenshot after enabling encryption to document the final configuration.

If you change the AMI, review the network and storage settings again before launch.

8. Install Nginx Automatically with User Data

8.1. Open Advanced Details

Scroll down and expand Advanced details.

Configure:

Setting Value
IAM instance profile Leave empty
Detailed CloudWatch monitoring Keep disabled; use basic monitoring
Metadata version V2 only / token required, if shown

The workshop-flowlogs-role role is configured for the flow log in section 5.4.

8.2. Enter the Script

Paste the complete script into User data:

#!/bin/bash
set -euxo pipefail
export DEBIAN_FRONTEND=noninteractive

apt-get -o Acquire::Retries=3 update
apt-get -o Acquire::Retries=3 -o DPkg::Lock::Timeout=120 install -y nginx

cat > /var/www/html/index.html <<'HTML'
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title>AWS Network Workshop</title>
</head>
<body>
  <h1>AWS Network Workshop</h1>
  <p>Nginx is running.</p>
</body>
</html>
HTML

systemctl enable --now nginx

The script performs the following tasks:

  1. Updates package lists.
  2. Installs Nginx.
  3. Creates an HTML page for testing.
  4. Enables and starts the Nginx service.

Leave User data has already been base64 encoded unchecked.

Enter user data before launching the instance. Verify the installation and website access in section 5.5.

9. Launch and Inspect EC2

9.1. Review Before Launch

Confirm that:

  • Number of instances is 1.
  • The correct AMI and t3.micro instance type are selected.
  • EC2 is in the public subnet.
  • Auto-assign public IP is enabled.
  • The correct security group is selected.
  • The root volume is 8 GiB and uses gp3.
  • Root volume encryption is enabled.
  • The complete user data script has been entered.

Choose Launch instance.

9.2. Inspect After Launch

  1. Choose View all instances.
  2. Open aws-network-workshop-web.
  3. Wait for the Running state and successful status checks.
  4. Under Details, verify the VPC, subnet, public IPv4, and private IPv4 addresses.
  5. Under Security, verify the security group and saved rules.
  6. Under Storage, record the root volume ID and inspect the volume’s encryption information.

Record the actual values:

11. Completion Checklist

Mark each item only after verifying the actual result in AWS:

  • The VPC and both subnets use the correct CIDR blocks.
  • The public route table has a default route to the internet gateway.
  • The private subnet uses the correct route table.
  • The saved HTTP 80 rule uses the workshop client’s IP address with /32.
  • Port 8080 remains absent from inbound allow rules.
  • Root volume encryption and Delete on termination are enabled.
  • User data was entered before launch.
  • EC2 is Running, status checks pass, and a public IPv4 address is assigned.
  • Resource IDs and IP addresses are recorded.
  • Screenshots of saved settings and the actual EC2 instance are added.

After completing these checks, continue to 5.4 — Monitoring Setup in us-east-1.

Keep the resources for the testing sections. Perform cleanup in section 5.9 after preserving the required evidence.
