Monitoring Setup

1. Objectives

This section configures network traffic collection and email notifications.

The components include:

  1. CloudWatch Logs stores traffic records.
  2. An IAM role allows VPC Flow Logs to publish logs.
  3. VPC Flow Logs collects accepted and rejected traffic.
  4. A metric filter counts rejected TCP 8080 records matching the lab conditions.
  5. A CloudWatch alarm evaluates the metric.
  6. Amazon SNS delivers notifications to the subscribed email address.

Work in United States (N. Virginia) — us-east-1, consistent with the deployment in section 5.3.

If correctly configured resources already exist, inspect them and capture evidence.

2. Required Information

Information Where to find it
AWS account ID AWS account menu; 12 digits
VPC ID VPC → Your VPCs
EC2 public IPv4 EC2 → Instances → select the instance → Details
EC2 private IPv4 The same Details tab
Workshop client’s public IP Source of the HTTP rule in the security group
Notification email An address where you can confirm the SNS subscription

In the JSON examples, replace ACCOUNT_ID with your actual account ID.

In the filter pattern:

  • Replace CLIENT_PUBLIC_IP with the workshop client’s public IP, without /32.
  • Replace EC2_PRIVATE_IP with the EC2 instance’s private IPv4 address.

If you use a policy previously prepared for Singapore, update its Region conditions and ARNs containing a Region to us-east-1. IAM role ARNs do not contain a Region component.

3. Create the CloudWatch Log Group

  1. Open CloudWatch.
  2. Confirm that N. Virginia is selected.
  3. Open Log Management. If the console displays a Logs group, choose Logs → Log groups.
  4. Choose Create log group, or Actions → Create log group.
  5. Configure:
Field Value
Log group name /workshop/network/flowlogs
Log class Standard
Retention 7 days
  1. Choose Create.

If retention was not configured during creation, return to the log group list, select the current value in the Retention column, and choose 7 days → Save.

The log group must use the Standard class to support metric filters.

4. Create the VPC Flow Logs IAM Role

4.1. Configure the Trust Policy

  1. Open IAM → Roles → Create role.
  2. Choose Custom trust policy.
  3. Paste the following JSON and replace ACCOUNT_ID:
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "vpc-flow-logs.amazonaws.com"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "aws:SourceAccount": "ACCOUNT_ID"
        },
        "ArnLike": {
          "aws:SourceArn": "arn:aws:ec2:us-east-1:ACCOUNT_ID:vpc-flow-log/*"
        }
      }
    }
  ]
}
  1. Choose Next.
  2. On Add permissions, continue without selecting a managed policy.
  3. Set Role name to workshop-flowlogs-role.
  4. Choose Create role.

The trust policy allows VPC Flow Logs to assume the role and restricts the source to the lab’s account and Region.

If the role already exists, open Trust relationships → Edit trust policy to inspect or update it.

Screenshot 2: Capture the Trust relationships tab showing the service principal and source conditions.

4.2. Grant Log Publishing Permissions

  1. Open workshop-flowlogs-role.
  2. Choose Permissions → Add permissions → Create inline policy.
  3. Choose JSON.
  4. Paste the following and replace ACCOUNT_ID:
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublishWorkshopFlowLogs",
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents",
        "logs:DescribeLogStreams"
      ],
      "Resource": [
        "arn:aws:logs:us-east-1:ACCOUNT_ID:log-group:/workshop/network/flowlogs",
        "arn:aws:logs:us-east-1:ACCOUNT_ID:log-group:/workshop/network/flowlogs:*"
      ]
    },
    {
      "Sid": "DescribeLogGroups",
      "Effect": "Allow",
      "Action": "logs:DescribeLogGroups",
      "Resource": "*"
    }
  ]
}
  1. Choose Next.
  2. Name the policy WorkshopFlowLogsPublish.
  3. Choose Create policy.

If this inline policy already exists, edit the existing policy.

Screenshot 3: Capture the saved permissions policy in the role.

4.3. Verify PassRole Permissions

The identity creating the flow log needs iam:PassRole permission for:

arn:aws:iam::ACCOUNT_ID:role/workshop-flowlogs-role

This permission belongs to the flow log creator. The service role’s permissions policy defines the log publishing operations the service can perform.

5. Create the VPC Flow Log

  1. Open VPC → Your VPCs.
  2. Select the workshop VPC.
  3. Choose Actions → Create flow log, or open Flow logs → Create flow log.
  4. Configure:
Field Value
Name, if shown aws-network-workshop-flowlogs
Filter All
Maximum aggregation interval 1 minute
Destination Send to CloudWatch Logs
Destination log group /workshop/network/flowlogs
Service access Use an existing role
IAM role workshop-flowlogs-role
Log record format AWS default format
  1. Choose Create flow log.
  2. Verify the Active state and log delivery information.

Keep AWS default format so the filter pattern in section 6 matches the field order.

Flow Logs requires time to aggregate and deliver data. A one-minute aggregation interval does not guarantee that records appear in CloudWatch within one minute.

Screenshot 4: Capture the flow log, its state, destination log group, and IAM role.

6. Create the Metric Filter

6.1. Enter the Filter Pattern

  1. Open CloudWatch → Log groups.
  2. Select /workshop/network/flowlogs.
  3. Choose Actions → Create metric filter.
  4. Enter the following Filter pattern on one line:
[version, accountid, interfaceid, srcaddr = "CLIENT_PUBLIC_IP", dstaddr = "EC2_PRIVATE_IP", srcport, dstport = 8080, protocol = 6, packets, bytes, start, end, action = "REJECT", logstatus = "OK"]

Replace both placeholders with actual IP addresses before creating the filter.

Condition Meaning
srcaddr Workshop client’s public IP
dstaddr EC2 private IPv4
dstport = 8080 Destination port used for testing
protocol = 6 TCP
action = "REJECT" Rejected traffic
logstatus = "OK" Traffic record logged normally

If matching logs already exist, you can use Test pattern to validate the filter. Distinguish pattern validation from the actual test evidence collected in section 5.5.

6.2. Configure the Metric

Choose Next and enter:

Field Value
Filter name rejected-tcp-8080
Metric namespace Workshop/Network
Metric name Rejected8080Flows
Metric value 1
Default value 0
Unit Count
Dimensions Leave empty

Choose Next → Create metric filter.

Each matching log record contributes a value of 1 to the metric.

Metric filters process new data after creation. The default value of 0 applies when logs are ingested but no records match; periods without log ingestion can still have missing data.

7.3. Allow CloudWatch to Publish Notifications

  1. Open aws-network-workshop-alerts.
  2. Choose Edit → Access policy.
  3. Add the following object to the existing policy’s Statement array.
  4. Replace ACCOUNT_ID with your actual account ID.
  5. Preserve existing statements and separate the objects with commas.
{
  "Sid": "AllowWorkshopAlarmPublish",
  "Effect": "Allow",
  "Principal": {
    "Service": "cloudwatch.amazonaws.com"
  },
  "Action": "sns:Publish",
  "Resource": "arn:aws:sns:us-east-1:ACCOUNT_ID:aws-network-workshop-alerts",
  "Condition": {
    "StringEquals": {
      "aws:SourceAccount": "ACCOUNT_ID"
    },
    "ArnEquals": {
      "aws:SourceArn": "arn:aws:cloudwatch:us-east-1:ACCOUNT_ID:alarm:aws-network-workshop-rejected-8080"
    }
  }
}
  1. Choose Save changes.

This statement allows the specified alarm to publish notifications to the topic.

Screenshot 7: Capture the saved access policy.

8. Create the CloudWatch Alarm

8.1. Select the Metric

  1. Open CloudWatch → Alarms → All alarms.
  2. Choose Create alarm → Select metric.
  3. Open the Workshop/Network namespace.
  4. Select the group without dimensions, usually shown as Metrics with no dimensions.
  5. Select Rejected8080Flows.
  6. Choose Select metric.

If the metric is not visible, generate new data after creating the filter:

  1. Keep port 8080 absent from the security group’s inbound allow rules.
  2. From the workshop client, try opening http://EC2_PUBLIC_IP:8080 several times, replacing EC2_PUBLIC_IP with the actual public IPv4.
  3. Wait for records to reach CloudWatch Logs and check the metric.
  4. Return to create the alarm.

After creating the alarm, perform a new test in section 5.5 to correlate the test time, logs, metric, and email.

8.2. Configure the Condition

Field Value
Statistic Sum
Period 5 minutes
Threshold type Static
Whenever metric is Greater/Equal
Threshold value 1
Datapoints to alarm 1 out of 1
Missing data treatment Treat missing data as good (not breaching)

The alarm condition is Sum >= 1 within a five-minute evaluation period.

Choose Next.

8.3. Configure Notifications

Under Configure actions:

Field Value
Alarm state trigger In alarm
Send a notification to Select an existing SNS topic
SNS topic aws-network-workshop-alerts

Choose Next and enter:

Field Value
Alarm name aws-network-workshop-rejected-8080
Description Notify when matching rejected TCP 8080 flow records are detected.

Review the Preview page and choose Create alarm.

10. Completion Checklist

  • Regional services use us-east-1.
  • The log group uses Standard class and seven-day retention.
  • The IAM role has the correct trust and permissions policies.
  • The flow log creator has the required PassRole permission.
  • The flow log is Active and uses All traffic and AWS default format.
  • The metric filter uses the correct source IP and private destination IP.
  • The metric is Workshop/Network → Rejected8080Flows.
  • The SNS email subscription is confirmed.
  • The topic policy permits the alarm to publish.
  • The alarm uses Sum, a threshold of >= 1, and the correct SNS topic.

An OK state caused by missing-data handling does not establish that the complete monitoring chain is working.

Continue to 5.5 — Testing to correlate the connection, REJECT record, metric, ALARM state, and received email.
